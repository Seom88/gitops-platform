# ADR-027: Rancher as Local Management Plane for the One-Node k3s Cluster

**Status:** Accepted · **Date:** 2026-11-05 · **Deciders:** Seom88 · **Related:** [ADR-005](005-longhorn-back-to-gitops.md), [ADR-014](014-cilium-cni-and-identity-networkpolicies.md), [ADR-018](018-tailscale-per-app-ingress.md), [ADR-019](019-single-node-bare-metal-migration.md), [ADR-022](022-nextcloud-on-kubernetes.md)

> **Outcome:** a dedicated Rancher server (wave 4, namespace `cattle-system`, single replica, Tailscale-fronted) becomes the visual/RBAC/catalog management surface for the one existing k3s cluster. **ArgoCD remains the only deployment engine**; Rancher manages nothing it is not explicitly given a downstream identity for.

## Context

The cluster is one homelab node ([ADR-019](019-single-node-bare-metal-migration.md), single-node k3s on a ThinkCentre). It already carries an observability/control plane entirely in this repo via the App-of-Apps pattern ([ADR-005](005-longhorn-back-to-gitops.md)) and exposes apps through per-app Tailscale Ingresses ([ADR-018](018-tailscale-per-app-ingress.md)). The motivation for adding Rancher here is practical, not enterprise-scale:

- A browser-based surface for cluster health, Helm catalog/secret review, alerts, and RBAC without relying only on `kubectl` + `k9s`.
- A UI for Fleet/system-upgrade and local-cluster lifecycle management (with strict scope: local cluster only).
- A single "platform UI" counterpart to the existing app-facing ingress set (`monitoring.lonk-mirfak.ts.net`, etc.), reachable only from the tailnet.

Constraints, deliberately inherited rather than renegotiated:

- **One node, warm restart headroom ~24 Gi free of pod-requested headroom**; Rancher is sized (500m/1Gi request, 4Gi limit) to leave everything else alone.
- **Immutable-GitOps deploy path.** ArgoCD pulls from git; CI never talks to the cluster. That stays true.
- **TLS at the edge.** The Tailscale operator terminates HTTPS on the tailnet worker proxies; the Rancher Ingress itself is a plain HTTP backend ([ADR-018](018-tailscale-per-app-ingress.md)).
- **Network policy discipline.** Every first-party namespace in this repo ships a gated `CiliumNetworkPolicy` ([ADR-014](014-cilium-cni-and-identity-networkpolicies.md)) — with one documented exception below.

## Decision

### 1. Rancher ships as a first-party wrapper chart, `platform/rancher/`

Pinned dependency `rancher` **2.15.3** (latest stable at time of writing; `kubeVersion < 1.37.0-0`, which is compatible with k3s v1.36.5 but **will block a k3s ≥ 1.37 upgrade** until the chart is bumped — a conscious debt recorded here).

Values are locked to the single-node reality:

| Key | Value | Why |
|---|---|---|
| `rancher.replicas` | `1` | Upstream defaults to 3; the node runs everything else. |
| `rancher.hostname` | `rancher.lonk-mirfak.ts.net` | URL/agent address; overridden via `values-dev.yaml` to `rancher-dev…` (ADR-018 device-name rule). |
| `rancher.tls` | `external` | TLS terminated at the Tailscale proxy; container keeps its HTTP listener on :80 (Rancher's headline "HTTPS-only" UI still applies to tailnet users' browser → proxy hop). |
| `rancher.networkExposure.type` | `none` | Renders **no** chart-owned Ingress/Gateway and therefore **no** cert-manager Certificate/Issuer. Exposure is solely `templates/tailscale-ingress.yaml`. |
| `rancher.useBundledSystemChart` | `true` | Packaged system charts; Rancher cannot silently depend on runtime fetches from `system-charts` on the first sync. |
| `rancher.priorityClassName` | `rancher-critical` | Survives node pressure; same class used by platform tiers. |
| `rancher.resources` | `500m/1Gi` req, `4Gi` mem limit | No CPU limit; memory cap prevents one component from OOM-killing the node. |
| `rancher.antiAffinity` | `preferred` | No-op at 1 replica but keeps multi-replica future-free of footguns. |

The wrapper owns: `cattle-system` namespace (privileged pod-security), the Tailscale Ingress (device name `rancher`), and `cilium-networkpolicies.yaml` (DNS, intra-ns, kube-apiserver 443/6443, Hubble, monitoring scrape, 80/443/444/8443/9443 ingress).

### 2. Wave 4, gated on `platformApps.enabled`

`gitops/templates/platform/04-rancher.yaml` (`sync-wave: 4`). It sits after the storage/observability tier (`-2` … `3`) and before the wave-5/6 app tier so a Rancher outage cannot cascade into user apps. ArgoCD never creates Rancher's CRDs — they are generated by the Rancher server at runtime. The Application uses `ServerSideApply=true` for clean first-sync of large CRD-adjacent manifests.

### 3. Local cluster only, no downstream provisioning

- **Local cluster is registered automatically** as `local` in Rancher's cluster registry.
- **No downstream cluster is added, and no provider cloud credentials are stored in this repo.** If/when a downstream cluster is onboarded (RKE2, k3s-in-k3s, etc.), that is a new decision domain with its own ADR.
- **Fleet is enabled (upstream default)** for the local cluster but is inert until a `GitRepo` is applied. Fleet could duplicate ArgoCD's role; for this repo, **ArgoCD remains the deploy/teardown/git-sync path and Rancher/Fleet is non-authoritative by convention**. Any divergent change applied through the Rancher UI is out-of-band and will be reconciled-away by ArgoCD on the next sync.

### 4. Bootstrap & operations model

- **No password is committed.** `bootstrapPassword` is empty by intent; on first boot Rancher creates one and the operator reads it once with:

  ```
  kubectl -n cattle-system get secret bootstrap-secret -o jsonpath='{.data.bootstrapPassword}' | base64 -d
  ```

  then optionally rotates from the UI. The SOPS path is deliberately unused (no need for another age key lifecycle for a one-shot local credential).
- **RBAC:** Rancher does not mint cluster admins; it exposes read-ish views for authenticated tailnet users (auth is Rancher's own local users or an OIDC provider — no OIDC is wired yet; a separate decision if added).
- **k3s/Rancher upgrades are never automatic.** System plans (`k3s` plan, `rancher-*` images) may exist in the UI but must never be left enabled without an explicit maintenance step; k3s stays owned by the provisioning/infra path, not by Rancher.
- **Runtime namespaces are out of the Cilium policy set.** Rancher creates `cattle-fleet-system`, `cattle-fleet-local-system`, `cattle-global-nt`, `rancher-operator-system` outside this chart; their network policy is **uncovered** until a policy chart exists for them (recorded here instead of papered over). The chart's policy names them explicitly as out-of-scope.

### 5. Explicitly rejected

- **Rancher in `apps/`** — apps are user-facing workloads; Rancher is control plane, like Longhorn/monitoring.
- **Rancher as the primary GitOps engine** — would split authority with ArgoCD and forfeit the app-of-apps/wave/SOPS/Cilium conventions this repo is built around.
- **`tls: ingress` + cert-manager Istio → issuer chain** — needless private CA machinery for a tailnet-only surface.
- **Multi-replica Rancher + Redis** — single node, single replica; RAM is wanted elsewhere.
- **Downstream cluster provisioning from day one** — adds Cilium/CAC/token surface without a consumer.

## Consequences

**Positive**
- A single, authenticated (tailnet-only) management UI for the cluster's own health and catalog.
- Zero new public exposure; zero new secrets in git.
- Any future "click-driven" operation is a reviewable step, never a silent drift: ArgoCD re-applies git on the next sync.

**Negative / debt**
- **k3s >= 1.37 blocked** until `rancher` chart is bumped past its `kubeVersion` ceiling.
- **Rancher increases baseline RAM**: server (≥1Gi) + `rancher-webhook` (200Mi-ish) + Fleet/system-upgrade-controller. Capacity headroom re-checked post-deploy; if pressure shows, limits go **down**, never replica counts.
- **Uncovered namespaces**: Fleet/operator runtime namespaces inherit *no* Cilium policy (Rancher-created). This is a known gap, not an implicit allow-all by design — the default Cilium stance in this cluster is otherwise allow-by-absence-of-deny; the roadmap item is an explicit policy set for `cattle-*` consumers before Fleet is given an active `GitRepo`.
- **Two management UIs exist** (Grafana for metrics, Rancher for inventory/RBAC). This is accepted as complementary: metrics vs inventory/config.

## Verification (first deploy)

1. `git push` → ArgoCD syncs wave 4.
2. `kubectl -n cattle-system get pods` → rancher/webhook healthy.
3. Retrieve bootstrap secret with the command above; log in at `https://rancher.lonk-mirfak.ts.net`. If the Tailscale edge answers 503/unreachable while everything in `cattle-system` is healthy, check `ts-operator-proxy-egress` (`platform/ts-operator`) for `cattle-system → TCP 80` before any app-side policy — it is the proxy→backend allowlist and was missing until 2026-11-05.
4. Confirm `local` cluster is `Active`; `cattle-fleet-local-system` pods green.
5. Confirm the Tailscale proxy HTTPS cert is valid (ts.net CA).
6. Decide *explicitly* whether to onboard Fleet; until then, Rancher is read/operate only.
7. Re-read `kubectl get ns cattle-*` — any new namespace is a candidate for its own policy chart before drift compounds.

## Alternatives considered

- **Portainer**: single-node Docker UI, but weaker k8s/RBAC/GitOps semantics; no Fleet equivalent.
- **Headlamp**: lighter k8s UI, but no local-cluster upgrade UX and no catalog UX; rejected for the stated intent.
- **Nothing**: status quo is `kubectl` + Grafana + k9s; works but does not give a shared, authenticated management surface for the household's non-operator members.
