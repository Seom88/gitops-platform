# ADR-023: Collabora Online (CODE) for Nextcloud — Second Per-App Ingress, HPA Off

**Status:** Accepted · **Date:** 2026-10-10 · **Deciders:** Seom88 · **Related:** [ADR-014](014-cilium-cni-and-identity-networkpolicies.md) (zero-trust policies), [ADR-018](018-per-app-tailscale-ingress.md) (per-app ingress + the `tailscaleIngress` block model), [ADR-022](022-nextcloud-on-kubernetes.md) (the Nextcloud app this extends), [ADR-019](019-single-node-bare-metal-migration.md) (single node)

## Context

The user asked for document editing on Nextcloud. The chart already carried the plumbing — upstream `nextcloud/nextcloud` 9.4.0 bundles a conditional subchart, `collabora` (real name `collabora-online` 1.1.60, image `collabora/code:25.04.9.4.1`) — and `apps/nextcloud/values.yaml` had `collabora.enabled: false`. Everything needed to turn it on is local: the subchart tgz already sits inside `charts/nextcloud-9.4.0.tgz`, so enabling the condition requires **no** `helm dependency update` and no new network fetch.

What the chart does *not* do is wire the two halves together. Collabora Online is a WOPI client that must be reachable by the **browser**, because coolwsd serves the editor iframe itself; Nextcloud is the WOPI host that fetches the file back. That split, plus the fact that TLS terminates at the tailscale proxy, is what this ADR records.

## Decision

**Enable the bundled subchart, expose it through a second per-app Tailscale Ingress, and close the four policy surfaces that a second pod in the same namespace needs. One replica, HPA off.**

- **Rendered name is `nextcloud-collabora`, not `-collabora-online`.** The upstream chart declares the dependency with `alias: collabora`, and Helm rewrites the subchart's `Chart.Name` to the alias, so its `fullname` helper builds `<release>-<alias>`. Getting this wrong produces an Ingress pointing at a Service that never exists — a silent 503 behind the proxy. `tailscaleIngress.collabora.service` spells it out, and the values comments say why.
- **Second Ingress, not a subpath on Nextcloud's.** `collabora.lonk-mirfak.ts.net` → Service `nextcloud-collabora`, ClusterIP 9980. `templates/tailscale-ingress.yaml` now loops over `.Values.tailscaleIngress` instead of hardcoding one object, so a second app is a values entry (the ADR-018 model) and not a new template.
- **`extra_params: --o:ssl.enable=false --o:ssl.termination=true`, `server_name: collabora.lonk-mirfak.ts.net:443`, `aliasgroups: [https://nextcloud.lonk-mirfak.ts.net:443]`.** coolwsd terminates no TLS itself, so it must know the proxy did: Tailscale `serve` sets `X-Forwarded-Proto: https` and `X-Forwarded-Host` (tailscale/tailscale#8224, ≥1.44), which is what makes coolwsd emit `https://` action URLs in the discovery document. Leaving `ssl.termination` off makes the document self-describe as `http` and the browser blocks a mixed-content iframe on an https page. The aliasgroup is the Origin coolwsd validates the editor against: the Nextcloud URL as the browser sees it.
- **`net.post_allow` needs no entry.** The pod CIDR (`10.42.0.0/16`) is already inside CODE's default allowlist (`10.0.0.0/8`), so the WOPI POSTs back to Nextcloud pass without widening that list.
- **HPA pinned off** (the subchart's own default is `true`). The chart README documents that scaling breaks collaborative editing: a document session must stay on one pod. With one replica there is nothing to balance, and per-document affinity hashing needs an ingress controller, which the tailscale proxy does not expose.
- **Resources: requests 200m/512Mi, limits 1500m/2Gi.** CODE's own guidance is 2Gi/1800m *per pod* for an HA footprint; a single-user single-replica pod on one node doesn't need it. The node reports ~13Gi free, so the ceiling is real but not generous.
- **Four policy surfaces, in two charts.** The namespace-wide policies use `endpointSelector: {}`, so they already cover the CODE pods — they just need ports: `nextcloud-allow-ingress` gains 9980 from the tailscale proxy (the browser path) and 9980 from host/remote-node/apiserver (coolwsd's startup/liveness/readiness probes hit `/` on 9980, not 80). And the **egress direction that is easy to miss**: `ts-operator-proxy-egress` in `platform/ts-operator` is an explicit namespace→port allowlist for the proxy pods, holding `nextcloud → 80` but not 9980. Without that one line the new Ingress 503s while every app-side policy looks correct. CODE's WOPI traffic in both directions itself needs no new rule: `WOPISrc` is the external tailnet hostname, so it rides the existing `world:443` egress rule as a non-cluster IP — documented in that rule's comment so nobody "tidies" it away.
- **The Nextcloud side is charted as an idempotent helm hook Job, not as a human step.** The image bundles and enables a new `office` overview app (v1.1.0) and ships **no** editing app: `richdocuments` comes from the app store (`occ app:install richdocuments`, 12.0.1 on NC 35), then `occ app:disable office` — the bundled `Office` app is confirmed to break document editing alongside richdocuments 12.0.0 on NC 35 — and `occ config:app:set richdocuments wopi_url --value=https://collabora.lonk-mirfak.ts.net` (set **before** the activation, because the CLI carries no Host and an empty value makes the fetch fail with "Could not detect any host"), followed by `occ richdocuments:activate-config`, which is the CLI equivalent of the **Save** button in Admin → Office: it re-fetches `/hosting/discovery` and `/hosting/capabilities` and rewrites what the app caches. The ordering rule is the whole design: a read-only reachability gate runs **first**, and only a reachable CODE lets the activation run — a FAILED `activate-config` DELETES the cached discovery document (observed on 12.0.1), so the failed job path exits before touching anything cache-shaped and there is no fallback that deletes files. That last step is not idempotent on its own — a fetch that fails while CODE is unreachable turns every file open into a 500 — which is why the whole sequence is wrapped in one `post-install,post-upgrade` hook Job that re-runs on every upgrade, tolerates an already-configured system (every step exits 0 when there is nothing to change), and proves the work by asserting the cached document exists afterward.

## Alternatives Considered

| Option | Tradeoff | Verdict |
|---|---|---|
| Subpaths (`/browser`, `/cool`, `/hosting`) on Nextcloud's existing Ingress | Saves one device and one cert; CODE generates absolute URLs from `server_name`, and the tailscale ingress cannot rewrite or strip a prefix, so the app breaks on path-aware clients | Rejected — fights the ingress, and ADR-018 exists precisely to stop subpath shims |
| Built-in CODE server (`richdocumentscode` app) | No second pod, no second Ingress, no extra policies; cold starts on first open and it runs LibreOffice inside the PHP pod | Rejected — it needs elevated capabilities in the same pod the repo keeps single-purpose, and it trades startup latency for nothing this single user needs |
| 2+ replicas behind the chart's `reverseProxy` nginx | Real session affinity via `WOPISrc` hashing | Deferred — `reverseProxy` does not exist in subchart 1.1.60, and one node with one user gains nothing from it |
| Bump to CODE 26.04 now | Newer LibreOffice, `/livez` + `/readyz` probes, compact `/cool/ws` websocket | Deferred — the compact URL is irrelevant behind a `/`-prefix proxy, but 26.04.2 distroless builds broke `extra_params` env parsing; stay on 25.04.9.4.1 until the chart bumps it deliberately |
| OnlyOffice / the Nextcloud+IONOS Euro-Office fork | Different fidelity profile on MS formats | Not considered — out of scope: the chart ships Collabora and the request was for Collabora |

## Consequences

### Positive

- One document editor, zero new operators, zero new images to scan as first-party: `collabora/code` is auto-discovered by `just validate-images` from the chart and lands in the advisory tier like every upstream subchart image.
- No new secret surface. CODE's admin console stays at the chart default credentials behind the tailnet — accepted because nothing outside the tailnet can reach it, and it is one SOPS secret away from the `nextcloud-admin` pattern if that changes.
- The recovery/upgrade story is unchanged: CODE is stateless (documents live on the Nextcloud PVC), so a redeploy or version bump is a `values.yaml` change with no data migration.

### Negative

- **Tailnet footprint grows by one device + one cert** (`collabora.lonk-mirfak.ts.net`). The same trade-off ADR-018 already accepted per app; Let's Encrypt quota is not close to tight at this scale.
- **The wiring spans two charts.** Enabling CODE now touches `apps/nextcloud` *and* `platform/ts-operator`; a change to either can break the other silently. Recorded here so the next reader checks both.
- **~512Mi–2Gi of the node's memory is committed for a feature that is idle most of the time.** Accepted, but it is the reason the limits are not the code's recommended 2Gi requests.
- **The wiring now has a real dependency on the app store.** `occ app:install richdocuments` fetches `apps.nextcloud.com` at upgrade time, so a synced release can fail when the network or that service is down — the price of not maintaining a private appstore. The failure is loud (the Job exits non-zero and ArgoCD marks the sync failed) rather than a silently disabled editor, which is why the install is the only step guarded by `|| true` plus a strict `app:enable`.
- **The hook Job needs the PVC it shares with the app Deployment.** It mounts the same `nextcloud-nextcloud` subPaths (`html`, `config` read-only, `data`) so `occ` reads the real `config.php` and writes app data next to the app's own: no database credentials in git and no env duplication. ReadWriteOnce is satisfied because the cluster is single node (ADR-019) and both pods land on `aleph`; adding a worker node requires the Job to be pinned to the same node as the app pod before it can still work.

## Verification

- `helm lint apps/nextcloud`, `helm lint platform/ts-operator` — 0 failures.
- `helm template nextcloud apps/nextcloud -n nextcloud` renders **2** Ingresses (`nextcloud` → `nextcloud:8080`, `collabora` → `nextcloud-collabora:9980`), and `nextcloud-collabora` exists in the same render as Service (ClusterIP 9980), Deployment (pod ports + all three probes on 9980), and ConfigMap (`aliasgroup1: https://nextcloud.lonk-mirfak.ts.net:443`, `server_name: collabora.lonk-mirfak.ts.net:443`, `extra_params: --o:ssl.enable=false --o:ssl.termination=true`, `envFrom` wired to it, resources 200m/512Mi–1500m/2Gi).
- `helm template ts-operator platform/ts-operator --set ciliumNetworkPolicy.enabled=true` renders `ts-operator-proxy-egress` with `namespace: nextcloud → {80, 9980}`; `nextcloud-allow-ingress` carries 9980 on both the tailscale-proxy and the probe rule, and no other port list changed.
- `gentle-ai review assess --cwd <repo> --json` → `medium` (`configuration_change` on the Cilium policy), under budget; parent re-rendered with the real release name rather than trusting the writer's `release-name` default, which is how the Service-name bug was caught.
- Live smoke after sync (owner checklist): pod 1/1; `collabora.lonk-mirfak.ts.net` answers **200** on `/hosting/discovery` and that document contains `https://collabora.lonk-mirfak.ts.net` action URLs (if it says `http`, `ssl.termination` or the proxy's forwarded headers are wrong); open a `.docx` from the Files app and confirm the editor loads and saves.
- Observed on first sync: `nextcloud-collabora` took ~2.5 min to reach 1/1 (two startup-probe failures before the kit finished booting), which is why the Job's discovery gate polls up to 5 min rather than curling once — a one-shot gate fails the release before CODE is ready. `nextcloud-allow-dns` and `nextcloud-allow-egress` both select `{}` (the whole namespace), so the Job pod's DNS and its `world:443` reachability need no new policy. From inside the app pod, `/hosting/discovery` returns 200 with a `<wopi-discovery>` body whose action URLs are `https`, confirming `ssl.termination=true` plus the proxy's forwarded headers.
- Observed on `richdocuments 12.0.1`: `occ richdocuments:activate-config` **exists** and does the Save button's work — it fetches `/hosting/discovery` and `/hosting/capabilities`, validates the mimetype response, detects the server (`Collabora Online Development Edition 25.04.9.4`), and reports the public browser URL as `https://collabora.lonk-mirfak.ts.net:443`. It requires `wopi_url` to be set **before** it runs: the CLI carries no Host, so with an empty value it prints `Could not detect any host`, fails the discovery fetch, and leaves nothing cached. Running it in that order is the difference between the wiring working and silently doing nothing.
- Observed idempotency (the rendered Job script run four times against the live pod, exit 0 each time): `app:install` prints `already installed`, `app:enable` prints `already enabled`, `app:disable office` on an already-disabled app prints `No such app enabled` and exits **0**, and `config:app:set` on an unchanged value prints `Config value were not updated` and exits **0**. The 12.0.1 cache path is `data/appdata_<id>/richdocuments/remoteData/{discovery,capabilities}` — the older documented `richdocuments/richdocuments/discovery.xml` layout does not exist, which is why that path never appears in the Job.
- Observed destructiveness, and the fix it forced: with CODE unreachable (a dead `wopi_url`), `activate-config` exits **1** and *deletes* the cached discovery document — a transient outage would have turned a working install into a broken one, and an `else` branch that cleared the cache on any non-zero exit made that worse. Proven after the fix: the isolated gate against a dead endpoint fails with exit 1 while the cached document stays untouched (44049 bytes), because the failed path now exits before any cache-shaped operation and the Job has no delete step at all.
- Ship-blocking detail for whoever applies this: `helm.sh/hook` resources exist only in the Helm release, not in the tracked manifests, and `hook-delete-policy: hook-succeeded` removes the Job on success — so after a green sync "no Job in `kubectl get job`" is success, not a missing template. Verify the outcome with `occ app:list` showing `richdocuments` enabled and `office` disabled, plus a non-empty `remoteData/discovery`.
- Expected failure mode if the proxy egress rule is missing: 503 from `collabora.lonk-mirfak.ts.net` while every app-side policy reads correct. Check `ts-operator-proxy-egress` first.
